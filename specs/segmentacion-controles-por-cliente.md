# Spec — Segmentación de controles por empresa (scope real)

> Pedido de Guillermo (2026-07-31): "cuando abrís Marval te aparecen los controles generales para todos los clientes, los generales de la herramienta que usa ese cliente (Meta4 o Axton), y los específicos de Marval. Hoy tenemos una batería de controles para Marval, pero cuando abro un cliente nuevo que no es Marval, no deberían aparecer esos controles."
>
> No es segmentación por usuario/rol (eso sigue fuera de alcance, `PRD.md` §7). Es segmentación por **cliente y por sistema de origen**.

**Punto de partida:** T4 construyó el mecanismo (`scope`, `scopeMeta`, `appliesWhen` en las 11 entradas del registry) pero dejó todos los controles en `scope: 'general'` / `appliesWhen: () => true` — o sea, los 11 aparecen para cualquier cliente. Esta tajada ata los predicados reales por primera vez.

**Decisiones tomadas por Guillermo (2026-07-31):**
1. **Clasificación:** `agrupadores` queda general (sirve para cualquier sistema); los otros 10 pasan a ser **exclusivos de MARVAL**. Ningún control queda como "general de Meta4" todavía — se van promoviendo desde Marval a medida que se confirme que aplican a cualquier cliente Meta4.
2. **Dónde se define:** el scope base vive en el código (`registry.js`); las excepciones por cliente se hacen desde `#/admin` vía `controlConfigs.status` (`forzado_activo` / `forzado_no_aplica` con motivo).
3. **Cliente sin controles aplicables:** los no aplicables se **ocultan del todo** (se retira la sección "Otros controles" que introdujo T4).

|---|---|
| **Guardrails** | Puede modificar: nuevo `js/controls/scope.js` (helper de resolución), `js/controls/registry.js` (los campos `scope`/`scopeMeta` de las 11 entradas — **no** su `run`/`summarize`/`renderResults`), `js/ui/controlsWizard.js` (filtrado + retiro de "Otros controles"), `js/ui/checklistView.js` (columnas del checklist según cliente), `js/ui/adminView.js` (columna informativa "aplica por scope", para que se entienda qué se está forzando), los tests afectados. No puede tocar: la lógica de cálculo de ningún control (guardrail transversal de `specs/plan-v2-t0-t6.md` §0); los 22 `code` del seed; el schema de `controlConfigs` (T5) — se usa el `status` que ya existe, no se agregan campos. |
| **Comportamientos a preservar** | Las corridas históricas siguen visibles y legibles aunque su control ya no aplique al cliente: `controlsResults.js` y `checklistView.js` resuelven `CONTROL_REGISTRY[row.controlId]` por id para pintar resultados guardados — ese lookup **no** se filtra por scope, sólo se filtra la *oferta* de controles nuevos a ejecutar. Un analista con corridas de Marval las sigue viendo igual. `agrupadores` sigue disponible para todos los clientes (incluido Marval). |
| **Scope** | Entra: (a) nuevo scope `'sistema'` con `scopeMeta.sourceSystems: ['meta4'\|'axton']`, que hoy **ningún control usa** pero es el mecanismo que permite promover un control de Marval a "general de Meta4" sin inventar nada nuevo después; (b) helper único `controlAppliesToClient(ctrl, client, config)` con precedencia **override de admin → scope/scopeMeta → appliesWhen**; (c) los 10 controles pasan a `scope: 'cliente'`, `scopeMeta: { clients: ['MARVAL'] }`; (d) el wizard lee `controlConfigs` del cliente y respeta `forzado_activo`/`forzado_no_aplica`/`no_aplica` — hoy esos estados se guardan pero nadie los lee, así que el override de admin pasa a funcionar de verdad; (e) se retira la sección "Otros controles" del wizard; (f) el checklist mensual muestra como columnas sólo los controles que aplican a ese cliente; (g) `#/admin` sigue listando los 11 controles (es el lugar donde se fuerza) más una columna informativa que dice si aplica por scope. Afuera: no se implementa el scope `'convenio'` con datos reales (el helper lo soporta, pero ningún control lo usa — no hay control de escala salarial todavía, ROADMAP 3.8); no se toca T10 (`clientCode`); no se agrega UI para editar scope desde admin (decisión 2: el scope base es código). |
| **Evals** | `tests/controlsScope.test.js` (nuevo, unit): con un cliente `MARVAL` (meta4) aplican los 11; con un cliente nuevo cualquiera (meta4 y axton) aplica **sólo** `agrupadores`; un control con `scope: 'sistema'` + `sourceSystems: ['meta4']` aplica a Marval y no a un cliente axton; `forzado_activo` hace aplicar un control que el scope excluía y `forzado_no_aplica` excluye uno que el scope incluía. `tests/controlsRegistryScope.test.js` reescrito (el assert "los 11 aplican a cualquier cliente" ya no vale — es exactamente lo que esta tajada cambia). `tests/e2e/controlsWizardScope.spec.js` reescrito: un cliente nuevo ve sólo "Cruce por Agrupadores" y **no** existe la sección "Otros controles". `tests/e2e/agrupadoresControl.spec.js` (T9) tiene que seguir pasando sin cambios — usa un cliente nuevo y el control general. |
| **Autonomía** | Decide solo: el nombre del scope nuevo (`'sistema'`, en español como los otros tres), la firma del helper, el orden de precedencia entre override y scope (el override de admin gana — es el propósito de `forzado_*` según T5), el texto de los mensajes de UI. Consulta antes de: mover cualquier control de los 10 a otra clasificación que no sea `MARVAL` (la clasificación la fijó Guillermo, no se reinterpreta); atar un control a un atributo del cliente vía `appliesWhen` (pluriempleo/holding/paymentUsd) — sigue pendiente de que Guillermo indique cuál corresponde, igual que en T4. |
| **Condición de salida** | Para cuando los tests de arriba pasan en CI y un cliente nuevo muestra sólo `agrupadores`. No implementa el scope `convenio` con datos reales, no construye la grilla cliente × control editable desde admin (decisión 2 la descartó), no arranca T10. |
